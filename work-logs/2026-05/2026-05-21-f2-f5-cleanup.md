## 2. 設計決策

### 2.1 F2 — `list_items` / `list` 用 `func.count`

從 `count_stmt = base.with_only_columns(InventoryItemORM.id)` + `len(...scalars().all())` 改為：
```python
count_stmt = select(func.count()).select_from(base.subquery())
total = sess.execute(count_stmt).scalar_one()
```

兩處：
- `inventory_repository.py:273-274`
- `material_request_repository.py:233-234`

**為何 `.select_from(base.subquery())` 而非 `.select_from(InventoryItemORM)`**：base 已加 WHERE 條件（farm_id / warehouse_id / below_safety_only），subquery wrap 直接複用所有 filter；不需重複貼條件。

### 2.2 F3 — `list_warehouses` 加 repo method

router 內 `with repo._sessionmaker() as sess:` 直接撈 ORM 違反 repo 封裝。加 `InventoryRepository.list_warehouses(farm_id: str) -> list[Warehouse]`，router 一行 call。

不破 API contract（response shape 不變）。

### 2.3 F4 — `_FARM_REGISTRY` lazy singleton 抽 shared

4 routers 各自重複：
- `modules/workflow/routers/inventory_router.py:75-92`
- `modules/workflow/routers/material_request_router.py:82-96`
- `modules/workflow/routers/approval_router.py:125-141`
- `modules/cost/routers/cost_ledger_router.py:57-72`

抽到 `shared/farm_registry_provider.py`：
- `resolve_farm_db_path(farm_id: str) -> str`：lazy singleton + import + lookup + raise HTTPException
- `reset_farm_registry()`：給 `set_*_factory(None)` 路徑用（清 singleton 讓下次 lazy 重 init）

各 router 移除 `_FARM_REGISTRY` global + `_resolve_farm_db_path`，改 call shared module。

**為何不 inject** 而是用 module singleton？
- 4 個 router 都用 FastAPI module-level state（非 DI），現狀就是這樣設計
- 全改 DI 是 scope creep（refactor 涵蓋面太大；不在 F4 scope）
- 改用 shared module 維持「同 process 同 singleton」語義，但消滅 4 份重複

**測試 hook**：保留 `reset_farm_registry()` public function 讓測試清 state；現有 `set_*_factory(None)` 流程改 call shared `reset_farm_registry()`。

### 2.4 F5 — `InventoryAdjustmentLog.actor_id` 改 Optional

支援系統自動 adjustment（如未來 dispatch hook 直接 adjust，無人工 actor）：
- domain `InventoryAdjustmentLog.actor_id: UUID` → `UUID | None = None`
- ORM `InventoryAdjustmentLogORM.actor_id`：`Mapped[str]` → `Mapped[Optional[str]]`（nullable=True）
- repo `adjust()` 簽名：`actor_id: UUID | None = None`
- repo `_log_to_domain`：`UUID(orm.actor_id) if orm.actor_id else None`
- schema `AdjustInventoryRequest.actor_id`：→ `Optional[UUID] = None`
- schema `AdjustmentLogResponse.actor_id`：→ `Optional[UUID] = None`

**ORM column 是否需要 migration？**
- 本專案 SQLite + `Base.metadata.create_all`，無正規 migration framework
- 新表沒問題；舊表 NULL 寫不進 NOT NULL 欄 → 但目前是 single-dev 階段，dev DB 隨時可重建
- 真正生產時走 alembic 加 migration（出 M4 release 時統一處理；本 issue scope 不含）

- F1 / F6（其他 follow-up）

- frontend（actor_id Optional 影響 frontend：但前端 `AdjustmentForm` 一律帶 actor_id，不影響；schema accept None 是後端兼容性，前端維持必填）

### 5.2 設計決策落實

- **F2 subquery 包 base**：選 `select(func.count()).select_from(base.subquery())` 而非 `select(func.count()).select_from(InventoryItemORM)` — base 已含所有 WHERE filter（farm_id / warehouse_id / below_safety_only / status），subquery wrap 直接複用；不需重複貼條件
- **F3 ordering 與既有 router 行為一致**：`is_default DESC, name ASC`（default 倉排首位給 UI 預選用）
- **F4 不改 DI**：4 router 都採 module-level state，全改 DI 涵蓋面太大；shared module 維持「同 process 同 singleton」語義消滅 4 份重複；`reset_farm_registry()` public 給 `set_*_factory(None)` 流程清 state 用
- **F5 field 順序**：`id` 移到 `actor_id` 前面，避開 dataclass「non-default before default」rule；所有現有 call site 都用 kwargs（test 3 處皆 kwargs），不破 positional 兼容
- **F5 ORM nullable 不寫 migration**：本專案 SQLite + `Base.metadata.create_all`，dev DB 隨時可重建；生產走 alembic 時統一處理（不在 F5 scope）
- **F5 frontend 顯示 fallback**：既有 `InventoryDetailDrawer.tsx:472` 直接 `log.actor_id.slice(-8)` 若拿到 null 會 runtime crash；改為 `actor_id ? …{last8} : ui('system', '系統')` 與 i18n 一致
