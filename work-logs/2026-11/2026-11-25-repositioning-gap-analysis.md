### 2.2 儲存容量實測

以 14 台機組、10 秒取樣、跑 1 小時寫進暫存 SQLite（`Storage.store_readings`）：

- 5,040 列、資料庫 21.2 MB，每列約 4.2 KB（其中 `scada_json` 平均 3.1 KB）。
- 換算：約 0.5 GB / 天、15 GB / 月、91 GB / 半年。
- 對照：範例資料包 07 的 `timeseries_raw.parquet`，12,960 列 1.46 MB，每列約 113 bytes（100 個 tag）。同樣資料量約 0.4 GB / 月、2.5 GB / 半年。這是由 6 小時的小檔外推，實際要再量。
- 批次生成速度：14 台 1 小時資料約 11 秒，一個月約 2.3 小時。

### 2.3 對前一天分析的影響

- 前一天對「出發前助理」的主要疑慮是真實資料拿不到、主要指標偏弱。新定位下資料來源是自己的仿真風場，這個瓶頸不存在；出發前助理變成對外 API 的一個可能消費端，不再是主線。
- EPIC-DS 沒有白做：凍結情境 + 標準答案是可重複評分的考卷；持續運轉的仿真風場是開放式的練習場。兩者共用警報目錄、PLC 保護層與可觀測事件白名單。
- 新的設計後果：Live 的機率式故障也要另存一份不對外的故障紀錄，否則事後無法核對助理的判斷。

### 2.4 建議的開發順序

1. 對外唯讀 API 與外部身分（只回可觀測資料）。最小、最快，RAG 助理可以立刻接現有的 Live。
2. 長時間運轉的基礎：保留期可設定、分層儲存（近期 SQLite、長期每日 Parquet 檔）、重啟續跑、72 小時穩定性測試。
3. 機率式故障產生器（各情境的發生率、可重現的亂數種子、不對外的故障紀錄）。
4. 運維閉環：警報開單、工單完工才修復、定檢造成計畫停機、可用率改由運轉狀態計算。
5. 成本模組吃模擬結果。
6. 物理加深與實測風況匯入，持續進行，不擋前面各項。
