## 2. 實際完成

### 2.1 做了什麼

- `modules/workflow/hooks.py`（新）：工單建立或狀態改變寫進資料庫之後，通知登記的 listener。`WorkOrderRepository.create` / `transition` 呼叫它。listener 出錯只記 log，不影響工單的操作。
- `modules/monitoring/server/om_loop.py`（新）：`OmLoop`。
  - `on_plc_event`：即時模擬的跳機（T1 / T2）或自動重啟被封鎖（A039）→ 開一張故障維修工單，帶警報碼。只寫事件碼、PLC 文字、訊號值與設定值。
  - `on_work_order`：開工 → 機組進維修模式；完工 → 清故障、復位、啟動；進行中的工單被撤 → 放掉機組。即時模擬暫停期間（產生情境的批次）收到的動作先記著，批次結束後才套用。
  - `classify` / `account` / `availability`：每次把讀值寫進歷史時，把每台機組歸到發電中 / 可發電但沒在發電 / 計畫停機 / 非計畫停機，累加秒數、發電量、停機少發的電。
- `server/storage.py`：`availability_hourly` 表（每台機組每小時一列）、`add_availability`、`availability_totals`。
- `server/data_broker.py`：`om_loop`（第一次取用才建立，沒開就不載入工單模組）；記 PLC 事件、寫入讀值、啟動模擬、批次結束四個地方接上。
- `server/app.py`：`WMOM_OM_LOOP`（伺服器預設開）；啟動時把閉環登記到工單的掛鉤，並把月報的可用率接到運轉狀態紀錄（`set_availability_provider`）。
- `server/routers/operations.py`（新）：`GET /api/operations/availability`。
- `server/routers/maintenance.py`：docstring 標示為舊介面（舊的 `work_orders` 表）。

### 2.2 完工修什麼（第一版：完工即修好）

| 工單 | 完工時 |
|---|---|
| 故障維修、帶警報碼 | 修掉預期會送出這個碼的故障；沒有這樣的故障就只復位 |
| 故障維修、A039（自動重啟被封鎖） | 修掉已經跳機鎖住機組的故障 |
| 故障維修、沒帶警報碼（手動開的） | 修掉該機組全部的故障 |
| 定檢、預防保養、試運轉 | 修掉該機組全部的故障 |

修復發生在現場完工（`finish`），不等簽核。操作員復位仍然修不好帶故障的機組。簽核退回視同重新開工。鎖著的機組沒有未結案的工單時，每 10 分鐘（風場時鐘）的檢查會補開一張。

### 2.5 驗證、code review 與回歸測試

**測試**：`test_om_loop.py` 43 項（其中 22 項是「每一個會跳機的故障情境走完一圈」：注入 → 跳機 → 自動開的工單逐張開工、完工 → 故障清掉、回到發電；16 個情境通過，6 個在測試的風況下 30 分鐘內不會鎖住機組，自動略過）。

**真伺服器**（`WMOM_AUTH_ENFORCE=true`、續跑與自動啟動都開、閉環用預設值）：

1. 注入 WT004 量測回路斷線 → 跳機 242 → 工單自動出現（`WO-LEGAC-202611-001`、故障維修、draft、警報碼 242），說明只有事件碼、PLC 文字、訊號值與設定值、發生時間。
2. 重啟伺服器（續跑）：跳機還鎖著、工單還在。
3. 用 API 派工、開工：機組進 Normal Stop，`SrvOn`＝1。
4. 完工：60 秒後沒有鎖存的跳機、模擬器裡沒有故障、WT004 回到發電（671 kW），工單狀態 `awaiting_signoff`。
5. `GET /api/operations/availability`：全場時間可用率 0.961；WT004 非計畫停機 1.8 分鐘、少發 14.3 kWh。
6. 用外部金鑰讀 `/api/ext/v1/events`：52 筆裡沒有任何工單、修復或故障情境的字樣；看得到的是復位（008）、跳機解除與狀態轉換。

**code review**（`code-reviewer` 子代理，對 24 個故障情境各走一遍流程）：盲測邊界守住、沒有死鎖或遞迴。1 項必須修與 6 項該補強的：

| 審查意見 | 處理 |
|---|---|
| 對沒被這張工單佔著、正在發電的機組完工，會把它復位（重現：簽核退回後再完工，功率 784 → 150 kW） | 完工只對停著或鎖著的機組復位；簽核退回視同重新開工；重建時讓進行中工單佔著的機組回維修模式 |
| A039 開的工單修不到任何故障，機組復位後又被鎖住 | 修掉已經跳機鎖住機組的故障 |
| 去重段（強制關閉後重跑最後幾秒）沒有擋開單 | 沒有照做：開單那一刻被強制關閉的話工單可能沒寫進去，重跑時要補上；已有未結案的同碼工單就不會重複。加了測試 |
| 暫停的判定太寬、記著的動作不會清 | 改成 broker 明確呼叫 `pause()` / `resume()`；`rebuild` 時清掉 |
| 工單被撤之後機組還鎖著，沒有任何工單接手 | 定期檢查補開（`ensure_work_orders`） |
| 關機時把別人設的可用率 provider 洗掉、閉環的開關留在全域 broker 上 | 只清自己登記的；關機時把閉環關回去 |
| 測試只驗一個故障情境 | 加了每一個會跳機的情境的參數化測試，以及退回、重建、A039、撤單的測試 |

### 2.7 回歸測試

- backend 全部第一次跑：2445 passed / 7 skipped / 1 xfailed / **1 failed**。失敗的是 `test_nuisance_events.py::test_data_before_a_farm_event_is_identical_to_a_run_without_it`，單獨跑與相鄰的檔案一起跑都過。
- 追到原因，和這次的改動無關：`wind_model.set_override` 用實際時間取「現在的自動風況」當漸變起點（解析度一分鐘），同一個測試裡先後建的兩座風場若剛好跨過實際時間的整分鐘，前幾分鐘的讀值就不同。重現：把 `wind_model.utc_now` 設在同一分鐘內 → 相同；跨過整分鐘 → 不同。
- 處理：測試固定住 `wind_model.utc_now`（只改測試）。模擬器本身的問題——帶風況覆寫的批次不保證逐位元可重現——另開 WMOM-20261126-03，這次沒有動風況模型。
- 修完重跑的結果見 §2.8。
